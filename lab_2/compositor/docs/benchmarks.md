# C++-бенчмарки

`compositor_bench` проводит одну серию для выбранной конфигурации. Go-кода,
перебора матрицы параметров и запуска дочерних процессов здесь нет: будущий
внешний оркестратор сможет запускать этот executable и читать JSON-отчёты.

```sh
cmake -S lab_2/compositor -B build/compositor -DCMAKE_BUILD_TYPE=Release
cmake --build build/compositor --parallel
./build/compositor/compositor_bench lab_2/compositor/configs/benchmark-example.json
```

## План запуска

```json
{
  "input": "example.json",
  "warmup": 2,
  "repetitions": 10,
  "report": "benchmark-report.json"
}
```

`input` — путь к обычной конфигурации композитора: canvas, render, rectangles,
output и необязательный logging. Из неё берутся сцена, параметры холста и режима.
`output` и `logging` проверяются существующим загрузчиком, но их приёмники не
создаются: бенчмарк не сохраняет PPM и не отправляет логи, в том числе в Loki.
Исходные настройки не изменяются. Пути input/report считаются от папки плана.
Родительская папка отчёта должна существовать; существующий отчёт заменяется
после успешной записи временного файла. Запрещено заменять план или входной конфиг.

Все четыре поля обязательны. `warmup`: 0–100000, `repetitions`: 1–100000.
Дробные/отрицательные числа, неизвестные поля и отсутствующие файлы отклоняются.
Без прогрева запуск разрешён для проверки и исследования холодного старта,
но для обычных сравнений используйте прогрев.

## Что именно измеряется

1. Загрузка файлов и генерация сцены.
2. Создание выбранного исполнителя и политики (пул один на всю серию).
3. Подготовка исходного холста и последовательного эталона.
4. Прогрев обеих реализаций.
5. Повторные парные замеры последовательной реализации и выбранного кандидата.
6. Подготовка статистики и сохранение JSON.

В каждой итерации копия исходного холста создаётся ДО начала измерения. Измеряемый
интервал содержит только `Compositor::render(scene, canvas)`: внутреннее
копирование для транзакции, создание сетки/мьютексов/отметок, обработку объектов,
ожидание окончания заданий и применение результата. Внешняя подготовка холста,
сравнение результата, разрушение итогового холста и запись отчёта не входят.
Используется `steady_clock`, единица отчёта — наносекунда (это не обещание
наносекундной точности часов).

Пул кандидата создаётся заранее и переиспользуется. Последовательный эталон
использует одну область размером с холст и NoLockPolicy. Такой базовый вариант
не зависит от подбираемого размера областей; его настройки явно записаны в отчёт.
Это сравнение полных конфигураций, а не изолированное измерение цены одного
мьютекса. У последовательного кандидата также используются его заданные размеры
сетки: он может отличаться по времени от базовой конфигурации.

В чётных итерациях сначала измеряется baseline, затем candidate, в нечётных —
наоборот. Это уменьшает постоянный эффект порядка, но не устраняет влияние
нагрузки ОС, частоты процессора и кешей. Проверка сама читает весь холст между
замерами. Прогрев выполняется сначала baseline, затем candidate.

## Корректность

Каждый прогревочный и измеренный результат сравнивается с последовательным
эталоном. Сравниваются полные PixelState: RGB, наличие winner, его приоритет и
индекс. Учитывается число несовпадающих пикселей. Проверка не входит в замер.
Исходный холст не изменяется; каждое повторение начинает с одинаковых данных.
Пустая сцена допускается, но измеряет быстрый путь без работы и не характеризует
масштабирование CPU-bound нагрузки.

При расхождении отчёт всё равно сохраняется, но comparison_eligible=false и
median_speedup=null. Исключения из композиции прерывают серию: неполный отчёт
не заменяет предыдущий результат.

## Небезопасный режим

Для parallel-unsafe процесс выводит предупреждение и помечает отчёт
unsafe_experiment=true. comparison_eligible всегда false, median_speedup всегда
null — даже при совпадении пикселей. Длительности и расхождения носят только
экспериментальный характер. Data race в C++ — UB; возможны авария, зависание или
недостоверный отчёт. Бенчмарк это не исправляет. Для опытов запускайте отдельный
процесс с внешним тайм-аутом; управление процессами будет задачей оркестратора.
Автоматические тесты используют unsafe только с непересекающимися объектами.

## Генератор сценариев

Необязательное поле `generate` заменяет список прямоугольников из input, сохраняя
остальные настройки:

```json
"generate": {
  "scenario": "mixed",
  "rectangles": 1000,
  "seed": 42
}
```

| Сценарий | Геометрия |
|---|---|
| sparse | По одному прямоугольнику внутри каждой ячейки сетки, без перекрытий |
| overlap | Крупные прямоугольники, сосредоточенные в центральной области |
| large | Прямоугольники от верхней левой части до правого нижнего края |
| mixed | Чередование крупных прямоугольников и небольших размером до 16×16 |

Генератор использует mt19937 и явно заданное преобразование целых чисел по
модулю. Это воспроизводимые сценарии, не статистически равномерная выборка.
RGB и приоритеты также определяются seed; приоритеты лежат в диапазоне -10…10.
Все генерируемые прямоугольники находятся внутри холста. Пограничные случаи
обрезки можно задавать обычным входным конфигом.

Для генератора размеры холста должны помещаться в положительный int;
число прямоугольников 0–10000000, seed — uint32. В sparse число объектов не может
превышать число пикселей. При большом числе объектов они становятся очень
маленькими. Пример: `configs/benchmark-generated.json`.

## Отчёт

Версия схемы — 1. Сохраняются:

- все измерения baseline/candidate в порядке выполнения каждой серии;
- несовпадения в прогреве и замерах;
- minimum, maximum, median, mean и population standard deviation;
- median_speedup = median(baseline) / median(candidate), только для корректного
  безопасного запуска и положительных медиан;
- режим, запрошенное число потоков, фактическое число работников, сетка;
- размеры/цвет холста и полный список прямоугольников, в исходном порядке;
- сценарий, seed и версия алгоритма генерации;
- компилятор, конфигурация сборки, платформа и hardware_concurrency;
- Git revision и dirty-состояние на момент конфигурации CMake;
- время формирования отчёта.

Полный список прямоугольников сохраняется для воспроизводимости независимо от
будущих изменений генератора. JSON может быть большим. hardware_concurrency —
подсказка о числе аппаратных потоков, не измерение физических ядер или CPU quota.
Модель CPU, питание, температура и фоновые процессы автоматически не фиксируются.
После изменения исходников повторно выполните CMake для обновления Git-метаданных.

Для сравнения режимов используйте одну сцену, Release-сборку, одинаковый компилятор
и одну машину. Не сравнивайте отчёт с sanitizers/debug с оптимизированной сборкой.
Начальный план исследования: 2 прогрева, 10 повторений, потоки 1/2/4/…,
области 8/16/32/64/128. Это стартовые параметры, а не найденные оптимумы.

## Ответственности

| Компонент | Назначение |
|---|---|
| BenchmarkPlanLoader | Чтение плана и получение сцены |
| SceneGenerator | Воспроизводимая генерация геометрии |
| createRenderComponents | Общее для приложения и бенчмарка создание режима |
| BenchmarkRunner | Прогрев и границы замеров |
| countMismatchedPixels | Проверка результата |
| summarize | Чистое вычисление статистики |
| IBenchmarkReportWriter | Контракт сохранения отчёта |
| JsonBenchmarkReportWriter | JSON-схема и запись отчёта |
| benchmark_main | Сборка зависимостей, запуск и коды выхода |

Коды выхода: 0 — серия завершена, результаты совпали; 1 — ошибка ввода,
исполнения или записи; 2 — неверные аргументы; 3 — несовпадение с эталоном.
Нулевой код unsafe-эксперимента не доказывает корректность его алгоритма.

## Тесты

Проверяются статистика на известных числах, цвет и метаданные, обнаружение
ошибочного исполнителя, повторения/прогрев, сохранность исходного холста,
воспроизводимость сценариев, отсутствие пересечений sparse, загрузка плана,
поля отчёта и запрет speedup для unsafe/ошибочных результатов. CLI-тест запускает
полную серию, проверяет отчёт и отсутствие PPM/логов из исходной конфигурации.
