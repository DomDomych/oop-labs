# Логирование

Модуль не зависит от Image, Scene, Compositor, пула вычислений или PPM.
Обычные определения находятся в `.cpp`. Публичные интерфейсы не раскрывают
Boost.JSON или libcurl.

## Компоненты и контракты

| Компонент | Ответственность |
|---|---|
| `LogRecord` | Время события, уровень, имя события и строковые поля |
| `ILogger` | Приём событий и явное завершение доставки через `flush` |
| `BufferedLogger` | Фильтрация уровня, ограниченный буфер, последовательная доставка каждому sink |
| `ILogSink` | Синхронная доставка пакета, без сохранения переданного span |
| `ILogFormatter` | Преобразование записи в одну строку без завершающего перевода строки |
| `JsonLogFormatter` | JSON с экранированием строк, вложенным объектом fields |
| `StreamLogSink` | Запись в заимствованный ostream; используется для stderr |
| `FileLogSink` | Владение файлом в режиме append и делегирование StreamLogSink |
| `LokiLogSink` | Метки потока, сортировка времён и создание запроса Loki Push API |
| `IHttpTransport` | JSON POST с ограничением времени ожидания |
| `CurlHttpTransport` | Необязательная реализация HTTP(S) через libcurl |
| `LoggingConfigParser` | Внутренний разбор необязательной секции JSON |
| `createLogger` | Сборка выбранных компонентов в прикладном слое |

Для нового места назначения реализуйте `ILogSink`; для нового формата —
`ILogFormatter`; для другого транспорта — `IHttpTransport`. Изменять вычислительное
ядро не требуется. Подключение нового типа через JSON добавляется в прикладную
сборку и её схему. `BufferedLogger` владеет sinks через unique_ptr, форматтеры
разделяются через shared_ptr<const ILogFormatter>. Переданный ostream должен
жить дольше sink. Sinks сами не обещают потокобезопасности: logger сериализует flush.

## Время и влияние на вычисления

`main` фиксирует system_clock и steady_clock до чтения конфигурации, затем
загружает данные, выполняет композицию и сохраняет изображение. После этого
фиксируется окончание. `program_started` и `program_finished` отправляются
пакетом, включая неуспешный запуск и неверное число аргументов.

`timestamp_ns` — строка с Unix-временем в наносекундах; `duration_ns` — строка
с длительностью, измеренной монотонными часами. Календарные часы могут быть
скорректированы ОС, поэтому для длительности используется steady_clock.
Время включает загрузку, подготовку компонентов и сохранение PPM, но не flush
логов. Это длительность основной работы, а не полное время жизни процесса:
последующая доставка, включая HTTP, тоже занимает время. Для исследования
вычислительного ядра нужны отдельные будущие замеры композиции.

Никаких сообщений из циклов обработки пикселей и фоновых потоков логирования
нет. Начальная запись содержит фактическое время старта, но появляется в выводе
только при flush в конце. При аварийном завершении, UB или отключении питания
буфер может быть утрачен. Это не журнал с гарантией сохранности после сбоя.

`log` потокобезопасен, не делает I/O и не выбрасывает исключения; создание
аргумента LogRecord до вызова может выбросить. `flush` можно вызывать во время
работы производителей: он забирает текущий пакет, новые записи попадут в следующий.
Перед финальным flush производителей нужно остановить. Деструкторы не отправляют
логи. Буфер ограничен числом записей, а не суммарным числом байтов; размер одного
сообщения определяет вызывающий код. При переполнении новые записи отбрасываются,
счётчик потерь возвращается в `FlushReport` и затем сбрасывается.

## Конфигурация

Старые конфигурации совместимы: без `logging` используются stderr, JSONL,
ёмкость 1024 и минимальный уровень info. Пример с консолью и файлом:

```json
"logging": {
  "console": true,
  "file": "run.jsonl",
  "capacity": 1024
}
```

Поля необязательны. Нужно оставить хотя бы одно место назначения. `capacity`
от 2 до 1000000; минимум сохраняет две обязательные записи запуска. Файл логов
дописывается, его родительская папка должна существовать. Относительный путь
считается от папки конфигурации; совпадение с конфигом или выходным изображением
отклоняется (включая существующие алиасы файлов). Пример целиком:
`configs/logging-example.json`.

Пример строки:

```json
{"timestamp_ns":"1793491200000000000","level":"info","event":"program_finished","fields":{"duration_ns":"12345678","error":"","exit_code":"0"}}
```

Уровни debug/info/warning/error доступны в API; минимальный уровень задаётся
конструктором BufferedLogger. Приложение использует info, чтобы обязательные
временные записи не исчезали из-за фильтрации.

## Loki

`LokiLogSink` доступен в базовой библиотеке с внедряемым транспортом. Реальная
отправка включается отдельно; нужны заголовки и библиотека libcurl:

```sh
cmake -S lab_2/compositor -B build/compositor -DCMAKE_BUILD_TYPE=Release -DCOMPOSITOR_WITH_LOKI_HTTP=ON
cmake --build build/compositor --parallel
./build/compositor/compositor lab_2/compositor/configs/loki-example.json
```

Конфигурация по умолчанию предполагает уже запущенный локальный Loki на порту
3100. Сервер и Grafana не запускаются автоматически. Без HTTP-опции конфигурация
с Loki явно отклоняется до отрисовки. Настройки:

```json
"loki": {
  "url": "http://localhost:3100/loki/api/v1/push",
  "labels": {"app": "compositor", "environment": "local"},
  "timeout_ms": 2000
}
```

URL обязателен; по умолчанию labels = {"app":"compositor"}, timeout_ms = 2000.
Тайм-аут от 1 до 60000 мс. Метки непустые, имена соответствуют
`[a-zA-Z_][a-zA-Z0-9_]*`. Для просмотра в Grafana: `{app="compositor"} | json`.

Пакет содержит один stream и строковые наносекундные timestamps согласно
[Loki HTTP API](https://grafana.com/docs/loki/latest/reference/loki-http-api/#ingest-logs).
Записи сортируются по времени внутри пакета; глобальный порядок между процессами
не гарантируется. Успех — HTTP 204. HTTP 260 (блокировка ingestion), 4xx, 5xx,
ошибки соединения и тайм-ауты сообщаются как ошибки sink. Повторов автоматически
нет: частичная доставка может уже состояться, а повтор создаст дубликаты.

Curl сохраняет проверку сертификатов HTTPS, не следует перенаправлениям и
ограничивает время запроса. Аутентификация и tenant-заголовки для облачных или
многопользовательских развёртываний пока не настраиваются; для них можно добавить
реализацию IHttpTransport. Текущая реализация рассчитана на локальный Loki без auth.

## Ошибки

После отказа одного sink выполняются попытки доставки остальным. Ошибки и число
потерянных записей возвращаются в FlushReport; сам logger не пишет рекурсивно в
себя. `main` печатает диагностику в stderr. При успешной основной работе, но
ошибке доставки возвращается код 3: изображение уже сохранено. При ошибке основной
работы остаётся её код 1 или 2; `exit_code` записи отражает именно основную работу.
Ошибка инициализации настроенного sink до render прерывает запуск с кодом 1,
при этом используется исходный консольный logger.

Для потоковых и файловых sinks при ошибке возможна частичная запись; для сетевого
тайм-аута неизвестно, принял ли сервер пакет. Недоставленные пакеты не хранятся
на диске. FlushReport не является гарантией exactly-once доставки.

## Проверки

`LoggingTests` проверяет фильтрацию, экранирование JSON, переполнение, независимость
sinks, многопоточную запись с параллельным flush, формат Loki, ошибки HTTP через
подставной транспорт, конфигурацию и append в файл. CLI-тест проверяет обязательные
временные записи для успешного и неуспешного запуска.
При включённом HTTP добавляется тест с локальным HTTP-сервером (Python 3): реальный
POST, статус 204, 500, 260, тайм-аут, сохранность PPM и независимая доставка в файл.
Настоящий сервер Loki для тестов не требуется.
